# RFC 002: OpenAPI → TypeScript Typed API Client

- **Status:** Draft
- **Date:** 2026-08-13
- **Author:** FinSight contributors
- **Tracker:** Issue TBD

## Context

`backend/src/main/resources/static/app.js` is a 1779-line IIFE that calls
`fetch()` with hand-written paths, query strings, and inline JSON
parsing. The API surface is documented in `docs/api.md` only; the static
frontend has no machine-readable contract, so a server-side rename of
`/api/research/stock` would silently break the UI.

`springdoc-openapi-starter-webmvc-ui` was added in commit `72b20b1` and
already exposes `/v3/api-docs` at runtime. The piece missing is a
build-time pipeline that turns that schema into typed TypeScript
clients.

## Goals

1. Generate a typed TypeScript client from `/v3/api-docs` at build
   time, so the static frontend cannot drift from the API contract.
2. Replace the 50+ `fetch()` call sites in `app.js` with typed
   methods (`api.stockAiAnalysis.analyze(symbol)`, etc.).
3. Catch breaking changes in CI via `openapi-diff` (a 3rd-party
   package, no extra cost).
4. Keep the static-html deployment model: a single `npm run build`
   step produces `frontend/dist/app.js` which Spring Boot serves
   from `/`. No Node runtime required at deploy time.

## Non-Goals

- Migrating the static frontend to a full SPA framework (covered
  separately in RFC 003).
- Generating server-side stubs (we already have a Spring server).
- Documenting non-public endpoints.

## Design

### Build-time codegen

Add a `frontend/` workspace that runs `openapi-typescript-codegen`
against the live backend during CI. The generated package lives at
`frontend/src/api/generated/` and is checked in (so contributors do
not need a running backend to build).

```jsonc
// frontend/package.json
{
  "scripts": {
    "api:generate": "openapi-typescript-codegen --input http://localhost:8080/v3/api-docs --output src/api/generated --client axios",
    "build": "tsc -p . && vite build",
    "test": "vitest run"
  }
}
```

### Module layout

```
frontend/
  package.json
  tsconfig.json
  vite.config.ts
  src/
    api/
      generated/        (gitignored, regenerated by `npm run api:generate`)
        index.ts
        models/
        services/
    api/
      index.ts          (typed wrappers)
      auth.ts
      research.ts
      watchlist.ts
      workflow.ts
    types.d.ts          (ambient declarations for window.finsight)
  test/
    api.test.ts
```

The typed wrappers (`api/auth.ts`, etc.) compose the generated
services with:

- **Request correlation**: every fetch sets `X-CSRF-Token` and
  `traceparent` headers.
- **Error normalisation**: throws `ApiError` with a `problemDetail`
  field, replacing today's `if (!response.ok) throw ...` blocks.
- **In-flight deduplication**: the existing `concurrentWaiter` and
  lease mechanism are surfaced as `once(key, fn)` so the UI never
  triggers two parallel analyses for the same symbol.

### Migration of `app.js`

`app.js` keeps its IIFE shape and continues to be the only file
loaded from `index.html` for now. We add a small shim that exposes
`window.finsight.api = api`; existing handlers call
`finsight.api.research.analyzeStock(symbol)` instead of
`fetch('/api/research/stock/...', {...})`. This is the first step of
RFC 003.

### CI integration

`api-lint` job: after the Maven build, boot the lightweight Spring
profile in a background process, wait for
`http://localhost:8080/v3/api-docs`, run
`openapi-typescript-codegen --input <spec>`, and assert that the
generated `index.ts` is byte-identical to the committed one. A diff
fails the job — this is what catches server-side renames.

`api-diff` job: compare the latest `master` spec with the PR's spec
using `openapi-diff`; produce a markdown report and post it as a
PR comment.

## Migration plan

1. Land `frontend/package.json`, `tsconfig.json`, `vite.config.ts`,
   and the build pipeline. Empty `frontend/dist/` is committed; the
   `index.html` still loads `/app.js`. CI does not yet require the
   pipeline.
2. Generate the first batch (auth + watchlist APIs) and migrate
   the corresponding `app.js` call sites.
3. Generate the second batch (research + workflow + market APIs)
   and migrate. Existing functionality must not regress.
4. Add the `api-lint` and `api-diff` jobs to `ci.yml`. The `api-lint`
   job is now required for PRs.
5. Document the workflow in `docs/development.md`.

## Open questions

- Generator library: `openapi-typescript-codegen` (axios) vs
  `openapi-typescript` (lightweight, fetch-only). The existing
  `app.js` already uses `fetch`, so `openapi-typescript` is the
  closer match. Decision: `openapi-typescript` (no axios dep).
- Should the generated files be committed or built per-CI? Pros of
  commit: instant IDE feedback, no bootstrap. Pros of build: no
  merge noise when the server changes. Decision: commit.
- Do we keep `app.js` as the entry point during the migration, or
  switch to a bundled `app.bundle.js`? Decision: keep `app.js` for
  the first PR, switch in RFC 003.

## Estimated LoC

- Build pipeline: ~250 LoC (`package.json`, configs, scripts)
- Generated (committed): ~600 LoC across ~30 model + service files
- Typed wrappers: ~700 LoC
- `app.js` migration patches: ~300 LoC of edits
- Tests: ~150 LoC
- **Total: ~2,000 LoC**
